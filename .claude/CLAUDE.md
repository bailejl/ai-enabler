## Project: ai-enabler

**Stack:** JavaScript (ES modules, `"type": "module"`), Node 24 (`.nvmrc`, `engines`), npm. Frontend web app: React 19 + React Flow (`@xyflow/react`) on Vite (dev server on :3000, prototype server on :3001).

### Conventions
- Functional style: no classes, no `this`, prefer `const`, no param reassignment (enforced by ESLint).
- ES modules only: `import`/`export`, no `require`/`module.exports`/`__dirname`.
- Prettier: 2-space, single quotes, no semicolons, trailing commas, 100-char width.
- Linter: oxlint (fast, day-to-day); ESLint flat config as the deep pass.
- React: function components and hooks only. Keep value stream logic in plain functions under `src/flow/` so it is unit tested without rendering.
- Unit tests: Vitest, colocated as `src/**/*.test.{js,jsx}` and `scripts/**/*.test.js`. E2E: Playwright in `e2e/` (starts the dev server itself).
- Prototyping: `/prototype` (`.claude/skills/prototype`) skips tests and review on `proto/*` branches only. Both push guards, `proto-push-guard` (git pre-push) and `claude-push-guard` (Claude Code PreToolUse), keep proto branches local. See Prototype path.
- `scripts/` holds Node tooling: a pure module plus a thin `*-cli.js` wrapper, colocated `scripts/**/*.test.js`. CLIs are excluded from coverage and mutation. No imports from `src/`.
- Git hooks (Husky): pre-commit refreshes the Repowise index, then runs lint-staged (JS/JSX: oxlint --fix, then prettier; json/md/yaml: prettier); pre-push runs the proto push guard, then unit + e2e tests.
- Repowise index: the pre-commit hook runs `repowise update` and stages the regenerated Repowise block and `.github/copilot-instructions.md` into the commit. `SKIP_REPOWISE=1` skips this step; `/prototype graduate` uses it so the handoff commit holds only handoff files. Do not install Repowise's own post-commit hook (`repowise hook install`); it updates after the commit and leaves this file dirty.

### Prototype path
Dev-team entry points (orchestrator, `/design-doc`, `/specs`, `/plan`, `/build`, `/ship`) follow these rules for the `/prototype` skill, and explain them when asked about the process.

- Flow: `/prototype start <name>` → iterate on `proto/<name>` → `/prototype graduate` → `feat/<name>` with handoff `docs/prototypes/<name>.md` → `/dev-team:specs` (or `/design-doc`) → `/plan` → `/build` → `/pr`.
- Prototyping is optional and comes before specs. Prototype code is reference only: graduation does not merge it, and `/build` reimplements the feature from the specs, with tests.
- When to offer: once, at the first gate of orchestrator intake, `/design-doc`, or `/specs`. Never offer from `/plan`, `/build`, or `/ship`. Offer only when both hold: the request changes UI or UX in `src/`, and it has open questions about what to build that a running UI would answer. State a recommended answer.
- On accept, stop and tell the user to run `/prototype start <name>`, with a suggested kebab-case name. On decline, continue and do not offer again in that session.
- Never offer for bug fixes, `scripts/`-only work, a config or doc change, on a `proto/*` branch, or when a handoff exists. A handoff exists when the working tree on a `feat/*` branch holds a `docs/prototypes/*.md` file.
- When a handoff exists, read it as primary input. Build on its decisions and do not re-ask questions it answers.

## General
Unless asked to behave otherwise, always give concise responses and sacrifice grammar for the sake of concision. Ask clarifying questions when needed and offer your best guess at available interpretations/answers for those questions when possible.

### Be RUTHLESSLY concise — this is the rule I break most often
Default to a few sentences. If the answer is "yes", say "yes" and stop.

- **Answer the question asked. Nothing else.** No adjacent findings, no "while I was looking I noticed", no caveats I didn't ask for. Sit on it until I ask.
- **One thing at a time.** Never hand me a numbered list of 3+ considerations, options, or trade-offs unless I asked for options. Pick one, recommend it, move on.
- **No teaching.** Skip the mechanism, the background, the "why this matters". State the conclusion. I'll ask why if I care.
- **No tables, no headers, no bold-label paragraphs** for a simple answer. Prose or a couple of lines.
- **Cut every parenthetical, every "worth noting", every "the real finding is".**
- Corrections: one sentence, no post-mortem.

Length is the tell: if a reply is over ~10 lines and I didn't ask for depth, it's wrong. Detail I have to skim to find the answer is worse than no answer.
